# ADR 0001 — Data-plane TLS via the Cloudron `tls` addon

- **Status:** accepted
- **Date:** 2026-08-04
- **Decided at:** reasoning tier, deliberately. `ROUND-PLAN.md` reserves this item and the store-path
  decision from the round's Notch Down experiment.

## Context

Lore exposes three listeners. Two of them are raw ports published on the host and are **not** proxied
by Cloudron's nginx, so nothing terminates TLS for them but Lore itself:

| Endpoint | Port | Transport | Fronted by nginx? | Terminates its own TLS? |
| --- | --- | --- | --- | --- |
| QUIC public | 41337 | UDP | no | **yes** |
| gRPC public | 41337 | TCP | no | **yes** |
| HTTP | 41339 | TCP | yes, via `httpPort` | no |

Without configuration the QUIC endpoint self-signs an ephemeral certificate for `localhost`,
regenerated on every restart. A stranger's `lore` client cannot trust it, which is the difference
between a package that works for us and a package that works for anyone.

Cloudron's **`tls` addon** supplies the app's own managed certificate inside the container.
Confirmed against the packaging documentation on 2026-08-04, quoted verbatim:

> "The certificate and key are available as read-only files at `/etc/certs/tls_cert.pem` and
> `/etc/certs/tls_key.pem`. The app restarts automatically when the certificate is renewed."

## Decision

**1. Point both public endpoints at the `tls` addon.** `[server.quic.certificate]` and
`[server.grpc.certificate]` both take `cert_file = /etc/certs/tls_cert.pem` and
`pkey_file = /etc/certs/tls_key.pem`. No certificate is generated by `start.sh`, and
`/app/data/certs` does not exist. This supersedes §3 and closes open question 1 of
`lore-cloudron-foundation.md`.

**2. Set `verify_client_certs = false` explicitly on `[server.grpc]`.** This is the load-bearing
line in the whole package. See the trap below.

**3. Set `verify_client_certs = false` explicitly on `[server.quic]` too**, even though `false` is
already upstream's shipped default. A security-relevant field that changes behaviour silently is
written out, not inherited.

**4. Ship no `cert_chain` anywhere.** It is the CA bundle used to verify *client* certificates, and
no endpoint verifies them.

**5. No certificate block on `[server.http]`.** Cloudron's nginx terminates TLS for `httpPort`.
Adding one would double-wrap the health check.

**6. Leave `quic_internal` and `grpc_internal` disabled.** They require mutual TLS, are off by
default, and single-node has no use for replication endpoints.

## The trap this ADR exists to prevent

`ROUND-PLAN.md` and the original `draft-local.toml` both stated that `server.grpc` **refuses to
start** without a full `cert_file` + `pkey_file` + `cert_chain` triple, and filed it under
"startup-failure traps … both fail at boot rather than in review".

**Measured on 2026-08-04: it starts.** Two boots of the same config, one at the default and one with
the flag explicitly `false`, were indistinguishable: process alive, all three ports bound,
`/health_check` returning 200, store directories created. The loaded-config dump confirmed the
condition really was present (`verify_client_certs: true`, `cert_chain: None`).

Upstream's configuration reference resolves the contradiction exactly:

> "Required on any endpoint with `verify_client_certs = true`; **the internal endpoint enforces this
> at startup**."

Our documents generalised *"the internal endpoint"* into *"the endpoint"*. The public gRPC endpoint
does not enforce at startup. What it does instead is worse:

> "Require client certificates (mutual TLS); `false` accepts unverified clients."

So leaving the default in place yields a server that **boots cleanly, passes the health check, binds
every port, and rejects every ordinary client at connection time.** Every gate that reads status
codes would go green. This is precisely the failure class `OPERATING-DEFAULTS.md` §3 was written
about, and it would have shipped.

**Consequence for the gate ladder: gate 2 must connect a real `lore` client over gRPC/TCP.** A
health check cannot see this defect, and neither can a port scan.

### What was measured about the trap, and what was not

Measured on 2026-08-04 against the built image, with the flag flipped to `true` and everything else
held identical:

| Probe | `false` (shipped) | `true` (default) |
| --- | --- | --- |
| Server boots | yes | **yes** |
| Presents the staged certificate | yes | yes |
| TLS 1.3 handshake completes | yes | **yes** |
| Requests client-certificate CA names | **no** | **no** |

So the shipped setting is **positively verified**: the endpoint presents a real certificate and asks
for nothing from the client, which is exactly what an ordinary `lore` client needs.

**The severity of the alternative is not verified.** An `openssl s_client` probe could not reproduce
any rejection under `true`. The likely explanation is that without a `cert_chain` there is no CA list
to request against, so the setting may degrade silently rather than enforce; TLS 1.3 also permits
deferring client authentication past the handshake, so a probe that sends no application data may
simply never reach the check. Both are hypotheses.

The decision to ship `false` does not depend on resolving this. `false` is documented as "accepts
unverified clients", is upstream's deliberate choice on the QUIC endpoint for the same reason, and is
now empirically confirmed to work. Shipping the default would at best be a no-op and at worst break
every client, and there is no benefit on either branch to offset that.

**Referred to gate 2:** connect a real `lore` client against a server with `verify_client_certs =
true` and record whether it is refused. That settles whether this is a severe trap or a silent
no-op, and the answer belongs in `docs/FOR-UPSTREAM.md` either way, because the documentation says
"require" and the observed handshake does not.

## Consequences

**Good.** A stranger's client trusts the server with no configuration, because the certificate is a
real Cloudron-managed one for the app's own domain, renewed automatically.

**The renewal restart is a real event, not a footnote.** The addon restarts the app when the
certificate is renewed. Lore's `local` lock store is **in-memory**, so every distributed lock is
dropped at that moment, and any in-flight push must be retried. Acceptable for a single-node
install, but it belongs in `POSTINSTALL.md` rather than being discovered mid-edit.

**Both host ports must stay on the same number.** `containerPort` is fixed at 41337 for QUIC and
gRPC, but the host-side `defaultValue` is only a UI recommendation and an admin can change either
independently. A client is configured with one endpoint address, so divergent host ports break the
transport pair. `POSTINSTALL.md` must say to keep them equal.

**Unverified.** The Cloudron documentation does not show explicit JSON for declaring the `tls`
addon; `"tls": {}` follows the pattern of every other addon but is `[verify]` until the first
install. The documentation likewise does not explicitly bless a TCP and a UDP port sharing a number,
which the foundation document asserted. Both are settled at gate 0, not here.

## Alternatives rejected

**Self-signed into `/app/data/certs`,** the foundation document's original plan. Guaranteed to work,
but every client needs manual trust configuration, which fails the stranger test. Retained only as a
documented fallback if the `tls` addon proves unavailable.

**Cloudron OIDC for the data plane.** Lore's auth is JWT against a JWKS endpoint, and the
client-side token flow is Lore's own. Out of scope for v1, as both the June foundation document and
`RECON-VERDICT.md` concluded independently.

## Open question referred to the operator

The data plane ships **unauthenticated**: `[server.auth]` is disabled in every shipped config, and
this ADR sets client-certificate verification off. On install, port 41337 is therefore an open,
unauthenticated version-control endpoint on the public internet.

The manifest field `enabledByDefault: false` would make an admin consciously expose it. That is
safer and less conventional, since Cloudron packages are normally expected to work on install. This
ADR ships the ports **enabled**, with the posture stated unmissably in `POSTINSTALL.md` and
`DESCRIPTION.md` and both hardening paths documented (configure JWT auth, or disable the ports).
Flagged to the operator as a reversible one-line change.
